# Database Structures & Notes

This document describes the MongoDB database schemas, collections, relationships, validations, and database risks for the **Hisab Management** database (`hisab_db`).

---

## Database Configuration
*   **Database Type**: MongoDB (NoSQL)
*   **Connection Utility**: [lib/db.ts](file:///e:/Home/hisab-management/lib/db.ts) (references [lib/mongodb-promise.ts](file:///e:/Home/hisab-management/lib/mongodb-promise.ts) for Client connection pooling, configured with pool limits `maxPoolSize: 10`, `minPoolSize: 5`).

## Database Relationships & Mappings
*   **One-to-Many**: One `space_id` maps to multiple expenses, hisab records, marriage records, and exactly one active configuration setting document.
*   **Many-to-One Collaboration**: Multiple `users` documents can contain the same `space_id` value (meaning they collaborate on a shared database canvas).
*   **Foreign-key Association (Loose)**: `expenses` documents can contain an `associatedId` referencing a `hisab_id` or `marriage_id` in external collections. This linkage is verified and maintained through route controllers during inserts, modifications, or deletions.

## Schema Validation
*   No database-level validations (e.g. MongoDB JSON schema rules) are applied.
*   Application-level model validations exist (such as `validateExpense` in `models/Expense.ts`) to check inputs before insertion.

## Integrity Risks & Optimization Notes
1.  **Missing Indexes**: There are no database indexes created explicitly in the project codebase. As database documents grow, queries filtering by `space_id` (used by every route) will trigger collection scans instead of index lookups, degrading response times.
    *   *Recommendation*: Create single-field index on `space_id` across `expenses`, `hisab`, `marriage_hisab`, `settings`, and `users`.
2.  **Cascading Deletes Integrity**: If a record inside `hisab` or `marriage_hisab` is deleted by directly modifying the collection (outside the specific DELETE routes), their linked associated items inside the `expenses` collection will remain as orphans.
3.  **No Distributed Transactions**: Since the application writes to multiple collections separately (e.g., logging a gift in `marriage_hisab` and then writing the corresponding expense in `expenses`), there is a risk of partial success if the database server disconnects mid-transaction.
